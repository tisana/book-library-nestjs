## Findings

### [P2] Abort both command blocks when predecessor verification fails

- File: `docs/upgrade/nestjs-12/release-runbook.md`, lines 54-59 and 67-70; defective guard at lines **56** and **68**.
- Both shell templates run `test -z "$(docker compose ... ps --status running -q app)"` and then unconditionally continue to replacement `up`. No fail-fast shell or explicit abort is specified. A plain `bash` execution of each exact block with a harmless Docker stub returning `surviving-old-container` from `ps` still invokes replacement `up` and exits 0. This contradicts the documented requirement to stop before starting any replacement if a predecessor remains. A failed Docker `ps` is another hazard: an empty substitution makes `test -z` succeed, so merely adding `set -e` is insufficient.
- Fix: run each template in a defined fail-fast shell/script, explicitly check the exit status of the `ps` assignment, and abort if any predecessor ID remains. Ensure `stop`, pull and readiness errors also abort the sequence. Keep ingress closed on failure. Apply the same controls to upgrade and rollback.
- Verification: mock both extracted blocks with a surviving predecessor and a failed `ps`; each must exit nonzero without calling `up`. Normal empty successful `ps` should proceed. No production command is needed.

### [P2] Put resource acquisition inside the rehearsal cleanup boundary

- File: `docs/upgrade/nestjs-12/evidence/t6/rollback-rehearsal.ts`, lines **41-57**, with `try` beginning at line **212** and cleanup at lines **326-333**.
- The script creates the disposable replica-set fixture and temporary directory, inspects Docker networking, and writes the secret-bearing mode0600 environment file before entering `try/finally`. Initial Docker/network or environment-file setup failure therefore skips cleanup. A bounded mock of the unchanged transpiled script with `docker network inspect` throwing produced `exitCode: 1`, `fixtureStarted: true`, `fixtureStopped: false`, `envDirectoryCreated: true`, `envDirectoryRemoved: false`. The fixture launches Mongo with `detached: true`, so missing its stop call can leave an owned process and disposable data behind. Also, if `fixture.stop()` throws in the current `finally`, environment-file removal is skipped.
- Fix: cover acquisition/setup with the outer `try/finally`, retain optional handles only for successfully acquired resources, and attempt fixture/container/environment cleanup independently so one cleanup failure cannot skip the others. Preserve a nonzero failure outcome and redact diagnostics. The fixture helper already owns cleanup for its own failed creation; do not duplicate that internal lifecycle.
- Verification: bounded dependency mocks for initial network failure, environment-file write failure and fixture cleanup failure should prove every acquired resource is cleaned or its cleanup attempted. Keep the actual completed runtime evidence historical; no expensive full rehearsal is necessary for this cleanup-only fix.
